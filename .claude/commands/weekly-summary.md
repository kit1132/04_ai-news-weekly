# weekly-summary — AIニュース週次サマリー生成

## 目的

kit1132 の3つのソースリポジトリの直近1週間分ダイジェストを集約し、週次サマリー Markdown を生成して main に直接 push する。

## 前提

- タイムゾーンは JST（Asia/Tokyo）

### ⚠️ 対象週の決め方（2026-07-26 変更・最重要）

**対象週 = 実行時点で「直前に完結した ISO 週」**（月曜〜日曜がすべて過去になっている週）。
**実行日を含む週は対象にしない。**

```bash
TODAY=$(TZ=Asia/Tokyo date +%Y-%m-%d)
DOW=$(TZ=Asia/Tokyo date +%u)        # 1=月曜 … 7=日曜
BACK=$((DOW - 1 + 7))                # 今週の月曜まで戻り、さらに7日前へ

# GNU date（Linux・クラウド実行環境）
TARGET_MON=$(date -d "$TODAY -${BACK} days" +%Y-%m-%d)
TARGET_SUN=$(date -d "$TODAY -$((BACK - 6)) days" +%Y-%m-%d)
TARGET_WEEK=$(date -d "$TARGET_MON" +%G-W%V)

# BSD date（macOS でローカル実行する場合）
# TARGET_MON=$(date -j -v-${BACK}d -f %Y-%m-%d "$TODAY" +%Y-%m-%d)
# TARGET_SUN=$(date -j -v-$((BACK - 6))d -f %Y-%m-%d "$TODAY" +%Y-%m-%d)
# TARGET_WEEK=$(date -j -f %Y-%m-%d "$TARGET_MON" +%G-W%V)
```

**必ず検算する**: `TARGET_SUN` が `TODAY` より前であること。満たさなければ生成を中止して報告する。

検証例（2026-07-27 月曜に実行した場合、macOS で実測）:

```
TODAY=2026-07-27  DOW=1  BACK=7
TARGET_MON=2026-07-20  TARGET_SUN=2026-07-26  TARGET_WEEK=2026-W30   ← 直前に完結した週
```

**この定義に変えた理由（2026-07-26）**

旧定義は「対象週＝実行日を含む ISO 週」で、毎週日曜 9:00 実行を前提にしていた。ところが実行日が日曜からズレて、
**直近3週が連続で「部分週」になっていた**（git コミット時刻の実測）。

```
W30  07/21(火)実行 → 対象07-20〜07-26 のうち2日分のみ  ← 部分週
W29  07/13(月)実行 → 対象07-13〜07-19 のうち1日分のみ  ← 部分週
W28  07/07(火)実行 → 対象07-06〜07-12 のうち2日分のみ  ← 部分週
W27  07/06(月)実行 → 完結
W25  06/21(日)実行 → 完結
```

新定義なら**実行曜日が何曜日にズレても常に完結した週**を対象にする。月曜に走れば前週、火曜にズレても同じ前週が対象になり、
その週は既に生成済みなので手順2でスキップされる。**部分週が構造的に発生しなくなる。**

- 想定スケジュールは **月曜 03:00 JST**（claude.ai Routines 側で設定する）。ただし上記のとおり実行日がズレても結果は変わらない
- **部分週は原則として生成しない。** 週の途中で手動実行したい場合のみ、明示的に指示された時に限り「部分週（〜実行日まで）」と冒頭注記して生成してよい
- 作業ブランチは必ず `main`。feature ブランチ・PR は作らない
- 入力リポジトリへは一切書き込まない（読み取り専用）

## 入力（読み取り専用・3リポ横断）

| リポ | リポタグ | パス |
|---|---|---|
| `kit1132/01_ai-news-Master` | `[master]` | `digests/<YYYY>/<MM>/ai-news-YYYY-MM-DD.md` |
| `kit1132/02_ai-news-Copilot` | `[copilot]` | `digests/<YYYY>/<MM>/ai-news-YYYY-MM-DD.md` |
| `kit1132/03_ai-news-industry` | `[industry]` | `digests/<YYYY>/<MM>/ai-news-YYYY-MM-DD.md` |

取得方法（作業ディレクトリが 04_ai-news-weekly の場合）:

```
git clone --depth 1 https://github.com/kit1132/01_ai-news-Master.git /tmp/src-master
git clone --depth 1 https://github.com/kit1132/02_ai-news-Copilot.git /tmp/src-copilot
git clone --depth 1 https://github.com/kit1132/03_ai-news-industry.git /tmp/src-industry
```

対象週7日 × 3リポ = 最大21ファイル。月をまたぐ週は正しい `<MM>` ディレクトリを参照する。存在しないファイルは「欠損」として記録する（リポタグ・日付）。

## 手順

1. ブランチを main に揃える:
   ```
   git fetch origin main
   git checkout main
   git pull origin main
   ```
2. **対象週を決める**（上の「対象週の決め方」参照）。実行日を含む週ではなく、**直前に完結した週**であることを検算する
3. 出力先 `weekly/<YYYY>/week-W<NN>.md` が既に存在する場合は、何も変更せず「当該週は生成済み」と通知して終了する
   - 実行日が想定（月曜）からズレても、対象週は同じなのでここでスキップされる。これが部分週を防ぐ仕組み
4. **欠番チェック**（2026-07-26 追加）: `weekly/<YYYY>/` の直近8週分のファイル名を確認し、抜けている ISO 週があれば
   **報告する**（自動生成はしない）。過去に W26（2026-06-22〜06-28）が誰にも気づかれず欠番になっていたため
5. 3リポの対象週分ダイジェストを読み取る
   - **21ファイル全欠損**: 生成を中止し、その旨を通知して終了
   - **一部欠損**: 取得できた分で生成し、冒頭に欠損リスト（リポタグ・日付の表）を明記
6. 下記フォーマットに従い週次サマリーを生成し、`weekly/<YYYY>/week-W<NN>.md` に保存する
7. `files.json` の配列先頭に新ファイルのパス（例: `weekly/2026/week-W24.md`）を追加する
8. コミット & プッシュ:
   ```
   git add weekly/ files.json
   git commit -m "Add AI news weekly summary for <YYYY>-W<NN>"
   git push origin main
   ```
9. push 後、`git log origin/main -1` で main に反映されたことを確認する

## 出力フォーマット（日本語）

```
# AI ニュース週次サマリー — <YYYY>-W<NN>（<月曜日付> 〜 <日曜日付>）

> 入力: 取得成功 N / 21（欠損があれば下の表に列挙）
> 生成日時: YYYY-MM-DD（JST）

（欠損がある場合のみ）
## ⚠️ 欠損ファイル通知
| 日付 | 欠損リポジトリ | 影響 |
|---|---|---|

## 今週のハイライト

3リポ横断でインパクト順に3〜5件。各件は `### N. タイトル — 一言の含意` の見出しに続けて
**要点** / **詳細** / **意味** の3段落で構成し、末尾に出典URLを箇条書きで付ける。

- **要点**: 何が起きて、なぜ重要か。**1〜2文・80字以内**。ここだけ読んで「読むか飛ばすか」を判断できるようにする
- **詳細**: 数値・スペック・日付・経緯。事実の裏付けを兼ねる。**1段落300字以内**（過去に880字の段落が生成されたため上限を設ける）
- **意味**: kit の仕事（AI/クラウド開発、コンサル提案）にどう関わるか

**書かないこと**:
- 一般論の助言（「〜を要件化すべき」「〜から着手するのが妥当」等）。読まれていないため2026-07-26に廃止した
- 材料がない段落を無理に埋めること。**該当する内容がなければその段落は省略する**（3段落を必ず埋めなくてよい）

## {カテゴリ名}

ハイライト以外のニュースをカテゴリごとに整理する。カテゴリ名は固定せず、当週の
3リポのダイジェストに出てきたカテゴリを自然に統合する（同名・類似は1つにまとめる）。
カテゴリ順は当週の件数または主要度順。

### {見出し} — [master]
- 詳細（重要項目には出典URL）

### {見出し} — [copilot][industry]
- 複数リポで重複する話題は1つに統合し、関与した全リポタグを付ける

## 来週の注目予定

3リポの「直近の注目予定」等から将来日付のイベントを統合し、日付順の箇条書きで。

## 改善メモ

3リポの「改善メモ」セクションを統合・重複排除して引き継ぐ。
リポ間の矛盾に気づいた場合もここに記録する。
```

### 統合の方針

- 同一ニュースが複数リポにある場合は情報量の多い方をベースに統合し、リポタグを併記する
- 矛盾する記述があれば両論併記し、改善メモに記録する
- URL は原文のまま記載する
- 日次の詳細をそのまま並べず、週単位での流れ・帰結（「週初の発表→週末の続報」など）が分かるように要約する

## 第1文の書き方（主体と述語）（2026-07-28 追加）

カテゴリ別項目の**第1文は、それ単独で意味が通る完全文にする**。

- 第1文は「〈主体〉が〈何を〉〈どうした〉」の形にし、**述語（動詞・助動詞）で終える**
  - 禁止: 「〜に変更。」「〜を追加。」「〜に切替。」「〜のみのメンテナンスリリース。」のような体言止め
  - 可: 「〜に変更した。」「〜を追加した。」「〜に切り替えた。」
- 主体が2つある場合は**操作・受益主体を優先**する
  - 操作・受益主体 = 誰が設定するか / 誰が使えるようになるか（開発者・管理者・エンドユーザー・対象プラン）
  - 発表主体 = 誰が出したか（Anthropic / OpenAI / Microsoft 等）。
    **本サマリーは3リポを横断するため発表主体は原則として省略しない**。
    ただし `— [master]` 等のリポタグや見出しで製品が特定できる場合は、繰り返しを避けてよい
- 太字ラベル・日付・バージョン番号（`7/21 v2.1.217:`）はラベルであって主体ではない。
  **ラベルがあっても主語を書いたことにはならない**。ラベルを隠しても第1文だけで通じること

**適用除外**: 「来週の注目予定」など将来日付のイベントを日付順に並べる節。

```
（悪い）7/21 v2.1.217: サブエージェント同時実行に既定 20 の上限（`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`）、ネスト生成を既定で禁止。
（良い）7/21 v2.1.217: サブエージェントの同時実行数に既定 20 の上限が付き、`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` で変更できる。ネスト生成は既定で禁止された。

（悪い）7/25 v2.1.220: バグ修正・安定性改善のみのメンテナンスリリース。
（良い）7/25 v2.1.220: 新機能はなく、バグ修正と安定性改善のみが入った。
```

2026-07-27 の実測（各ソース最新10ファイル・ハイライト・改善メモ・日付一覧を除く）では、
**主語よりも「述語で終わらないこと」が壊れていた。weekly は5ソース中で最も低い。**

| ソース | 項目数 | 主語あり | 述語で終わる | 両方満たす | 項目平均字数 |
|---|---|---|---|---|---|
| Master | 46 | 54% | 26% | 22% | 306字 |
| Copilot | 108 | 44% | 31% | 11% | 154字 |
| industry | 70 | 46% | 16% | 14% | 134字 |
| **weekly** | **580** | **33%** | **6%** | **2%** | **113字** |
| daily | 116 | 51% | 26% | 17% | 197字 |

weekly は述語で終わるのが **6%**、両方満たすのが **2%** しかない。
原因は changelog 列挙が「日付 + バージョン:」をラベルにして体言止めで並ぶ形になっていること。
バージョン列挙も1件ずつ完全文にすること。

⚠️ **文字数と引き換えにしない。** このルールは文を長くする方向に働く。
「冗長な前置き不要」は引き続き有効で、**項目平均字数 136字（＝適用前113字の+20%）を超えたら書きすぎ**。
02 Copilot に先行適用した 07-28 分では、述語で終わる率 31%→91% に対し項目平均字数は 154字→155字（+0.6%）だった。
**文字数を増やさずに達成できる**。測定は `scripts/measure-subject-rate.py`（01_ai-news 親ディレクトリ）で行う。

## 太字（`**...**`）の使い方

太字は「あとで検索・引用したくなる語」だけに使う。**文や節をまるごと太字にしない**。

- **1項目（`###` 単位）につき太字は3箇所まで**
- **1箇所は20字以内**の語句に限る。それを超える長さは太字にしない
- 対象は固有名詞＋バージョン（`Claude Code v2.1.220`）、金額（`$100M`）、日付、`%` などの数値
- 強調したい主張は太字ではなく**文の順序**（結論を先に書く）で示す
- 目安: 本文の太字比率は **10%以下**

2026-07-26 の実測（各ソース最新10ファイル・改善メモ除外）では、太字が
「多すぎる」と「1回が長すぎる」の2つの形で崩れていた。

| ソース | 太字率 | 1項目あたり | 1箇所の平均長 | 20字超の割合 |
|---|---|---|---|---|
| Copilot | 21.5% | 4.7箇所 | 26.1字 | 59% |
| daily | 18.7% | 4.6箇所 | 18.9字 | 40% |
| Master | 13.3% | 4.4箇所 | 15.6字 | 34% |
| weekly | 8.2% | 2.6箇所 | 14.3字 | 27% |
| industry | 6.5% | 0.5箇所 | 41.6字 | 82% |

太字が本文の2割を占めると、どこが重要かが判別できなくなる（太字が意味を失う）。
industry のように「回数は少ないが1回が41字」も同じ結果を招くため、回数と長さの
両方を守ること。
